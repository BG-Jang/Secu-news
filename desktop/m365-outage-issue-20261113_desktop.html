2026년 11월 13일자 스페셜 덱. 축: '공격이 아니라도 창구는 막힌다' — 가용성 사안은 기밀성·무결성과 다른 두 개의 축으로, 이번 장애는 그것이 한꺼번에 드러난 사례다. 모든 시각은 ET(동부시간) 기준이며, MS의 공지 언어는 원문 표현('예기치 않게 사용 불가', '구성 변경 롤백 검토')을 그대로 유지했다. 11-13 현재 root cause 미확정 상태의 스냅샷임을 각 장에 병기한다.

Incident Overview

무엇이, 언제, 얼마나 —
확인된 사실 정리

11.12 13:26 ET 시작 · Americas Exchange 장애로 출발 → 전 지역·전 서비스 확산
공식 확인 사항 (MS 관리자 센터 공지·BleepingComputer)
  • 11월 12일 목요일, MS는 먼저 Teams 단독 사고(TM1550488, 9:45~10:53 ET)를 겪었다 — 북·남미에서 메시지 발송 지연·실패, 대화 생성 오류, 채팅 조회 문제가 발생했고 '인프라 내 자원 경합(resource contention)'을 원인으로 밝힌 뒤 완전 해결을 통보했다
  • 같은 날 13:26 ET부터 광범위 사고(MO1550821)가 시작됐다 — Exchange Online·Teams·SharePoint Online·Microsoft 365 Copilot·Defender XDR 연결 불가, 초기 Americas 표적에서 "어떤 지역 사용자든 영향 가능"으로 확대 — 다운디텍터 피크 약 13만 건의 제보(Outlook·Word·Excel·PowerPoint·SharePoint·OneDrive·Copilot), 구글 워크스페이스 사용자가 아웃룩 클라이언트 경유 접속 장애를 호소한 사례도 보고됐다
  • MS는 "전체 트래픽 증가가 아니라 다수 서버의 예기치 않은 사용 불가가 남은 인프라를 압박한 것"으로 규정하고, 모든 배포 중단 + 전 세계 인프라로 연결 트래픽 재분산 + 영향 서버 재시작을 진행했다 — 저녁 업데이트: 복구 노력이 예상만큼 효과를 내지 못했고, 영향 서버의 '핵심 프로세스'가 포화돼 용량을 상실한 것을 발견; 일부 서버 복귀 후 안정 확인, 서비스 완전 복구 시점은 미확정
출처MS 서비스 헬스(MO1550821·TM1550488) · BleepingComputer(11.12) · InterestingEngineering

'13만 건'은 다운디텍터 사용자 제보 집계로 실제 영향 사용자 수의 대리지표일 뿐이다(중복·과소·과대 보고 포함). 실무적으로 중요한 것은 공지 체계 쪽 신호: EX(MO) 두 어드바이저가 동시에 열리고, Teams 선행 사고와 본 사고의 연관성을 MS가 부인도 확인도 하지 않았다는 점 — '관련 미확인'은 정보 공백이지 무관이 아니다.

Root Cause Anatomy

'건강검진 실패'는 어떻게
서버를 죽이는가

자동 헬스체크 실패 → 서버 배제 → 잔여 인프라 과부하 → 연쇄 포화의 악순환
복구 과정에서 드러된 인과 사슬 (MS 업데이트·SecurityWeek 종합)
  • 1단계 — 서버들이 자동 건강검진(health check)을 통과하지 못해 서비스에서 빠졌다: 헬스체크는 서버 정상성을 판정해 트래픽 배정을 좌우하는 장치로, 그 실패 자체가 '용량 상실'로 작동했다 — MS는 문제 검사 컴포넌트를 우회하는 워크어라운드를 시험했고, 대안 검증 방식이 일부 서버에서 통하면서 확산 적용 중이었다
  • 2단계 — 빠진 서버의 몫을 남은 서버가 떠안으면서 과부하: MS는 "트래픽 증가분이 과부하를 설명할 수준이 아니다"라고 명시 — 즉 수요가 늘어난 게 아니라 공급(유효 서버 수)이 줄었다 — 영향 서버에서 elevated processor usage도 관측돼 원인과 결과가 서로를 키우는 구조였다
  • 3단계 — 포화의 정체가 '보안 연결을 수립하는 프로세스(a process that establishes secure connections)'로 지목됐다: 이 프로세스가 압도돼 서버들이 요청 처리를 중단한 것 — MS는 장애 시작과 시점이 겹치는 최근 네트워크 구성 변경 소수의 롤백을 진행하며 효과를 모니터링했다(SecurityWeek 21:00 ET 시점에도 root cause 미확정, 사이버 공격 증거 없음)
출처MS 공지 원문 · SecurityWeek · InterestingEngineering

교훈은 '생존 편향된 자동화'다: 헬스체크는 아픈 서버를 격리해 트래픽을 지키지만, 격리 기준이 틀리면 healthy한 서버까지 대거 배제해 인위적 용량 붕괴(cascading capacity loss)를 만든다. TLS·토큰 같은 연결 계층 프로세스가 포화 지점이라는 점도 typical — 암호화 연산은 CPU 집약적이고, 요청 재시도는 폭주를 가속한다(백프레셔 없이). 그리고 구성 변경과 장애의 시간적 일치만 확인됐을 뿐 인과는 미확정 상태다.

Attack or Not?

'공격 증거 없음'과
'원인 불명' 사이의 공백

패치 튜즈데이(1,094건) 이틀 뒤 — 악성 아웃룩 제로-day(CVE-2026-124194)과도 시간 겹침
쟁점 분석
  • MS는 서비스 어드바이저에서 악성 활동 증거를 공개하지 않았고, SecurityWeek도 "여전히 조사 중, 사이버 공격 증거 없음"을 제목급 사실로 명시했다 — 이를 '공격 아님 확정'으로 읽으면 안 된다: 미확정과 무증거는 다른 상태다
  • 공백을 채우려는 추측들이 돌았다: 일부 사이트가 '사이버 공격설' 기사 제목을 달았고(SecurityWeek가 직접 반박), 커뮤니티에서는 DNS·윈도우 업데이트 음모론이 단골로 소환됐다 — 패치 튜즈데이(1,094개 결함, 악용 확인된 아웃룩 스푸핑 CVE-2026-124194 포함)로부터 이틀 뒤라는 시간적 근접이 추측에 연료를 줬지만, MS 어드바이저는 해당 취약점을 장애와 연결하지 않았다
  • 지금까지의 공식 사실 사슬은 전부 내부 요인 쪽을 가리킨다: 자원 경합 → 서버 사용 불가 → 헬스체크 실패 → 보안 연결 프로세스 포화 → 구성 변경 롤백 — 외부 침투 흔적은 어느 공지에도 없다 — 단 root cause 발표 전까지 최종 판정은 유보가 정답이다
출처SecurityWeek(공격설 반박 보도) · MS 어드바이저 · BleepingComputer

대량 장애의 2차 피해는 정보다: 'Outage = cyberattack' 식 프레이밍은 피싱 캠페인의 최적 무대다("계정 확인"을 가장한 사칭 메일이 장애 직후 급증하는 패턴). 실제로 이번에도 ransomnews 류 사이트가 공격설 제목으로 트래픽을 모았다 — SecurityWeek가 "Was the outage caused by a cyberattack?" 섹션을 따로 만들어 부재를 명시한 이유. 조직은 장애 기간에 '장애 사칭' 통신 채널(공식 도메인·알림 톤) 검증 지침을 발동해야 한다.

Deep Dive 1

하나의 창구에 국가를 걸었다 —
M365 단일 의존성의 청구서

구조 분석
  • 이번 장애의 영향 목록은 사실상 현대 사무 그 자체다: 메일(Exchange)·회의(Teams)·문서(Word·Excel·PowerPoint)·저장소(SharePoint·OneDrive)·AI 어시스턴트(Copilot)·심지어 보안 관제(Defender XDR)까지 — 보안 도구가 함께 죽은 것이 특히 예민하다: 사고 대응 채널과 모니터링이 같은 창구에 있었다
  • 'Exchange 비의존 요소는 기능 유지'라는 MS 단서가 방증하듯, 영향은 결합도 지도를 따라 번졌다 — 아웃룩으로 구글 메일을 쓰던 사용자까지 막힌 것처럼, 클라이언트·인증·동기화 공유 계층이 경계를 넘은 전파 경로였다
  • 금보원 사고(11.9)와 이번 장애는 같은 주제를 다른 축에서 때렸다: 하나는 기밀성(신뢰 기관 침해), 하나는 가용성(신뢰 플랫폼 정지) — 금융권·공공의 '제3자 리스크' 실사가 벤더 보안 등급(기밀성 중심)에 치우쳐 있었다면, 이번이 요구하는 것은 벤더 가용성 리스크의 정량화(SLA 크레딧이 아니라 업무 연속 관점)다
출처BleepingComputer·SecurityWeek 영향 보도 종합

Defender XDR 피격은 IR 관점에서 최악의 조합이다: 사고 대응 조직이 가장 필요한 시간에 대응 도구를 잃는다. 최소 연습 과제 — (1) M365 불가 가정의 48시간 커뮤니케이션 플랜(대체 메일·채팅 채널과 직원 연락처), (2) 보안 관제 세컨드 아이(SIEM 로그가 M365 경유라면 이중 수집 경로), (3) Copilot 의존 워크플로우의 수동 폴백. '장애 시' 문서를 이번 주에 한 번 실행해 보는 것만으로 격차가 드러난다.

Deep Dive 2

SLA는 이 문제를
해결하지 못한다 —
보상 너머의 계약 설계

월 99.9% SLA와 '전사 업무 정지'는 양립한다 — 크레딧은 손해가 아니라 위약금
쟁점 분석
  • 클라우드 SLA의 구조적 한계: 가용성 퍼센티지는 월 평균으로 계산돼, 업무 시간대 집중 정지(이번 같은 6시간 안팎)는 크레딧 몇 %로 청산된다 — 그러나 기업의 실제 손실(회의·결재·고객 응대 정지, 보안 관제 공백)은 크레딧과 무관하다: SLA는 손해배상 설계가 아니라 위약금 설계다
  • '배포 중단'이 MS의 첫 조치였다는 점이 역설을 보여준다: 벤더 스스로 변경 관리(change management)를 사고 대응 수단으로 쓸 만큼, 대규모 클라우드의 최대 리스크는 '변경'이다 — 고객 측도 동일하게, M365 조건부 접근 정책·엔터프라이즈 설정 변경의 창( )과 롤백 계획이 지금 있는가
  • 투명성 관행 평가: MS는 이번엔 어드바이저+X 실시간 업데이트로 '트래픽 증가 아님', '헬스체크 우회 시험', '구성 롤백 중' 같은 생생한 단계를 공개했다 — 과거 대비 개선이나, root cause·피해 규모(정확한 영향 고객 수) 부재는 여전히 관행의 하한이다: 사고 커뮤니케이션은 '무엇을 알리지 않는가'로 평가된다
출처MS 공지·X 업데이트 타임라인 · SecurityWeek 보도 종합

조달 관점 후속 질문: 계약 갱신 시 '장애 고지 SLA(몇 분 내 통보)', '사고 후 RCA 공개 의무', '다중 지역 페일오버 보장' 조항을 협상 대상으로 올릴 때 이번 장애가 사례로 기능한다. 개별 기업이 바꿀 수 있는 건 작지만, '복구 진행 중' 공지를 액션으로 번역하는 훈련(대체 채널 가동 기준)은 오늘부터 가능하다.
