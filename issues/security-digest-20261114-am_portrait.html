CVE-2026-123039(DynamicCLI 루트 상승) 제로데이 — 수십 개 고객 대상 실공격 확인 · 11.13 긴급 핫픽스
공격 체인 (Check Point 보고·BleepingComputer 종합)
  • 결함 구조: Gaia OS의 DynamicCLI 데몬(dynamic_server)이 root로 실행되며 세계쓰기 가능 로컬 소켓(/tmp/dynamic_socket)을 리슨하는데 연결 프로세스를 인증하지 않는다 — 로컬 인증 사용자만 있으면 루트 명령 실행 가능 — Check Point는 "고객 수십 곳"에 대한 활성 악용을 확인하고 핫픽스(sk1000362)를 배포, 즉시 적용 불가 시 dynamic_server 정지·재시작 금지를 임시 완화책으로 권고했다
  • 실전 체인: PHP2Shell(CVE-2026-109618/109619, PHP 긴급 패치 10.21 · 악용 시도는 그 나흘 전부터 · CISA KEV 10.26)로 모바일 액세스 포털 침투 → CVE-2026-123039 루트 상승 → 웹셸+TSGA 백도어(TSProxy 통신 컴포넌트) 설치 → gogo 스캐너로 찾은 내부 VMware ESXi 호스트로 피벗 — 최종 단계에서 destroy_v6 와이퍼가 재귀 삭제 + 제로 필트로 복구 시도까지 방해
  • 1차 물결(10.30)은 이스라엘 기관 대상, 파괴 단계에서 'Dream Security Ltd.'를 참조하는 DREAM_ANNEXATION.txt 정치적 메모를 남기고 몸값 협상을 명시적으로 거부 — Check Point는 위장작전(false flag) 가능성을 제기하며, TSGA/TSProxy를 Ivanti 공격에서 목격된 PhiliKit·중국 계열 UNC5221과 '잠정적' 연결했지만 현 증거로는 귀속 불확정 — 11.2의 2차 물결(다국가·다업종)은 파괴 활동 없이 후속 동작 미확인
출처Check Point 어드바이저·위협 보고 · BleepingComputer(11.13)

CISA가 경고한 'PHP2Shell+Fragnesia 커널 결함 체이닝'과 별개로, Check Point 경계에서 관측된 조합은 PHP2Shell+DynamicCLI다 — 웹셸→로컬 루트 상승이라는 고전 문법이 방화벽 OS에서 재현된 것. IoC: upload_progress_pwn 포함 세션 파일, 예상 밖 CPconfigdaemon 프로세스/바이너리, 방화벽 로그 공백, 게이트웨이→ESxi 무단 SSH. 관리 서버·게이트웨이 전체에 11월 잠보 핫픽스, 인터넷 노출 포털 우선.

Deep Dive 1

방화벽은 왜 침투의 발판이 되는가 —
'관리 평면'이라는 구조적 결함

구조 분석
  • Check Point 사건은 경계 보안 제품의 역설을 또 기록한다 — 인터넷에 노출된 '관리·원격 접속 평면'(Mobile Access 포털)이 공격 표면의 정점이다: 데이터 플레인 방어는 수십 년 강화됐지만, 관리 평면은 웹 스택(PHP) 위에 OS 데몬 루프가 얹힌 채 방치돼 왔다 — 9월 CVE-2026-93616(관리 서버)·CVE-2026-85102(게이트웨이) 무권한 RCE 제로데이에 이어 이번이 최근 시리즈의 세 번째 장이고, CISA KEV에 오른 Check Point 결함만 5건(2건은 랜섬웨어 조직 악용)
  • 와이퍼의 목표 선택이 시사적이다: ESXi는 엔터프라이즈 가상화의 핵심이자 보통 백업·스냅샷이 연결된 자산 — destroy_v6의 제로 필트는 '돈이 아닌 파괴' 의도의 기술적 증거이며, 정치적 메모+협상 거부는 전통 랜섬 경제 모델과 갈라진다 — Check Point 스스로 false flag 가능성을 열어둔 만큼, PhiliKit/UNC5221 연결은 가설 단계다(확정 명명 금지)
  • 연쇄 관성: 게이트웨이는 내부망 전 구간 라우팅·ACL을 아는 '지도 보유자' — 여기서 ESXi로 한 번 피벗하면 방화벽이 막아주던 동서 트래픽 구간의 통제가 역으로 공격자에게 읽힌다: 금보원(평가 데이터)과 같은 축 — '보안 자산이 가진 내부 지식'이 유출 시 최대 payload가 되는 패턴
출처Check Point 보고 · BleepingComputer · CISA KEV 내역 종합

Check Point 제품군은 '관리 트래픽 OOB 격리'가 권고사항이 아니라 필수다: 관리 서버·게이트웨이 SSH/웹 관리를 대역 외 네트워크로 분리, 인터넷 노출 포털 최소화, 그리고 이미 노출된 게이트웨이는 '패치=안전'이 아니므로 IoC 감사(upload_progress_pwn 세션 파일, CPconfigdaemon 이상, 로그 공백, 게이트웨이→ESXi SSH)를 병행해야 한다. ESxi 운영 조직은 게이트웨이 사고와 무관하게 하이퍼ervisor 접근 로그를 대조할 것.

  • 이번 주 네 사안은 각각 한 계층의 '믿음의 근거'를 표적으로 삼았다: 방화벽 뒤면 안전(경계), CI는 내 코드만 실행(빌드), 하드웨어가 호스트를 대신해 지키기(하드웨어), 원본이 죽어도 백업이 있다(복구) — 공격자들은 각 명제의 예외 지점(노출된 관리 평면, 외부 PR 자동 실행, 부팅 시 초기화 경쟁, 사업자 단일 의존)만 찔렀다
  • 공통 방어 원칙은 '같은 계층 내 이중화'가 아니라 '교차 검증'으로 이동했다: CI 시크릿은 OIDC 단기 자격+PR 승인 게이트(외부 기여 워크플로우 기본 차단), 기밀 컴퓨팅은 CSP 펌웨어 적용 상태의 제3자 확인+앱 레벨 암호화 병행, 백업은 BYOK+복구 훈련 시 무결성 검증, 방화벽은 구성 드리프트 감시와 네트워크 분리 — 각 층이 서로를 증명하는 구조가 필요하다
  • 그리고 어제의 MS365 장애·Apify까지 같은 문장 안에 선다: '통과한 자격'에 이어 '기대던 가용성'까지 무너지면서, 단일 벤더·단일 계층 의존이 이번 주 내내 반복 청구서를 발행했다 — 주간 리스크 레지스터에 '경계/빌드/하드웨어/복구 4계층의 각 최후 수단'을 적어두고 분기마다 하나씩 실패 시나리오를 연습하는 것이 현실적 대응이다
