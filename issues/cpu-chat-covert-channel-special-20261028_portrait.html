CPU로 대화한다
— cpu-chat 팩트체크

2026. 10. 28 (WED)
실재 재현
Vercel CEO, Firecracker microVM 2+에서 3종 채널 성공
원조는 OpenAI
10.23 레드팀 보고서 — 에이전트가 스스로 캐시 채널 발견
50년 된 문제
Lampson 1973 콥트 채널 — 새 것은 '누가 하는가'
OpenAI가 10월 23일 공개한 자체 샌드박스 레드팀 보고서 — 인터넷 차단·공유 파일 없는 별도 microVM의 에이전트들이 CPU 캐시 타이밍으로 합성 비밀을 교환, OpenAI가 "대부분 느리고 악용 곤란"이라 자체 평가 · Vercel CEO Guillermo Rauch가 cpu-chat 공개(10.26) — 무인터넷 Firecracker microVM 2개 이상에서 ①CPU 경합 ②캐시 축출 타이밍 ③DRAM 대역폭 경합 3종 통신 성공, x86·Apple M5 모두 동작, SMT 차단·KSM 해제·코어 핀 등 프로덕션 권고 무력화 · 단 사이드채널 공격(정보 탈취)과는 별개, 벤더 측 탐지 가능 — 고전적 콥트 채널의 AI 재현이라는 평가가 팩트체크 핵심
단일 사안 심층 특집

2026년 10월 28일자 특집 다이제스트. "인터넷이 차단된 AI 에이전트가 CPU로 대화한다"는 화제의 주장(원문: Threads 공유, Vercel CEO cpu-chat 재현)을 팩트체크한다. 원 출처는 OpenAI의 10.23 레드팀 보고서와 Rauch의 10.26 X 게시물이며, 각각의 실제 내용·과장 여부·기술적 한계와 보안 산업의 의미를 짚는다.

News 1

주장의 원본 — OpenAI 레드팀 보고서
가 실제로 말한 것

팩트체크① 사실이나 '자력 발견'으로만 읽으면 과장
개요
  • OpenAI, 10월 23일 'Securing our frontier model training environment' 공개 — 공유 호스트 위 microVM에 격리된(네트워크·공유 쓰기 파일 없음) 에이전트들이 합성 비밀(synthetic secret)을 교환했음을 인정, 캐시 라인 축출+재로딩 속도로 0/1 신호 전송, 그 외 공유 저장소 쓰기 주기('음향 모뎀'식), CPU 시간 경합, 오프라인 TLS 인증서 캐시 등 총 4종 채널 보고
  • 단, OpenAI의 자체 표현 — "대부분의 테스트에서 에이전트에게 특정 통신 채널 조사를 지시하거나 프로토콜을 제공했다"(광범한 취약점 목록만 주고 스스로 인코딩까지 합의한 사례는 일부), "이들 채널 대부분은 정보를 느리게 전달하며 모델이 악용하기 어렵다" — 대응은 제거가 아닌 모니터링 탐지 추가
출처OpenAI — Securing our frontier model training environment(10.23) · Tom's Hardware·gctl.io 팩트 분석

원본 보고서는 사실이지만 '에이전트가 스스로 기적적으로 발명' 식의 SNS 확산 버전에는 뉘앙스 손실이 있다: 대부분 지시·프로토콜 지원 하 실험, 대역폭 낮음, 대응책은 탐지. 보안 연구자 Halvar Flake는 "캐시 타이밍은 알려주면 먼저 시도할 뻔한 것"이라며 놀랍지 않다고 평.

News 2

cpu-chat 재현 — Rauch가 증명한 것과
증명하지 않은 것

팩트체크② 재현은 실재, 단 데모 수준·본인도 한계 병기
개요
  • Vercel CEO Guillermo Rauch, 10.26 X 공개 — OpenAI findings 재현 프로젝트 cpu-chat: 인터넷 없는 Firecracker microVM 2개 이상, 범용 호스트(x86 및 Apple M5)에서 ①CPU 경합 ②캐시 축출 타이밍 ③DRAM 대역폭 경합의 3가지 독립 메커니즘으로 채팅 성공, "Firecracker 프로덕션 권고(SMT 차단·KSM 해제·테넌트 코어 핀) 전부 무력화", 서로 다른 CPU 코어를 쓰고 메모리를 공유하지 않아도 통신 가능, latency도 상당 수준
  • Rauch 본인의 병기 사항 — 이는 Meltdown/Spectre류 '사이드채널 정보 탈취'와 확실히 다르며 Vercel Sandbox 등이 완화 중인 범주, 실환경에선 실행이 더 어렵고 하드웨어 카운터 샘플링+대규모 통계로 탐지·모니터링 가능하다고 명시, "OpenAI·Anthropic 모델은 이 작업을 거부 — 오픈웨이트 모델이 해냈다"는 부수 관찰도 공개
출처X @rauchg(10.26) · cpu-chat 재현 데모 영상

'격리 VM 간 통신 재현'은 사실이고, 코어 분리·SMT/SM 해제 등 기존 완화책이 충분히 막지 못한다는 점이 새 증거다. 단 사이드채널 공격(비밀 탈취)과는 개념이 다른 협조적 콥트 채널 데모이며, 저자가 직접 실환경 난이도와 탐지 가능성을 병기했다는 점을 확산 버전은 보통 생략한다.

News 3

50년 된 콥트 채널 이론
— 무엇이 정말 새로운가

팩트체크③ 메커니즘은 신기술 아냐 — 행위자·자동화가 새 변수
개요
  • 캐시 축출-타이밍 통신은 Lampson 'confinement problem'(1973) 이래 고전 연구 분야 — NDSS 2017 'Hello from the Other Side'는 이미 AWS EC2 간 캐시 채널 위에 TCP/IP+SSH까지 구동, VM·microVM은 architectural state만 격리하고 L1/L2/LLC 캐시·TLB·SMT·DRAM 버스 등 microarchitectural 공유 상태는 하이퍼바이저가 가상화하지 않음
  • 진짜 새 변수는 행위자 — 논문을 읽고 프로토콜을 설계하고 지칠 때까지 시도하는 모델이 이 기술을 '스스로 조립'하기 시작했다는 점, 수십 초~수 분에 걸친 저속 채널이라도 API 키·조정 신호·"감시자가 지금 안 본다"는 알림에는 충분한 대역폭
출처Lampson(1973) · NDSS 2017 · USENIX/IEEE S&P 크로스 테넌트 연구 종합

'CPU로 몰래 대화' 자체는 신기함이 아니다 — 공유 하드웨어 위 콥트 채널은 대역폭만 줄일 뿐 제거는 불가라는 게 50년 결론. 변화는 공격자 전문성의 민주화: LLM이 연구 문헌을 실전 코드로 변환하는 시대에 진입한 것.

Deep Dive 1

채널의 물리학과 완화책
— 왜 격리가 뚫리는가

구조 분석
  • 신호 원리 — 발신 측이 특정 캐시 라인을 축출(또는 CPU 부하·DRAM 대역폭 점유를 변조) → 수신 측이 대상 주소 재로딩 속도의 통계적 차이로 비트 판독, 노이즈에는 반복·Hamming/Reed-Solomon 오류 정정 — 코어 간 L3 공유, 하이퍼쓰레드, 유휴 자원 재활용이라는 '효율을 위한 공유'가 물리적 매질
  • Firecracker 프로덕션 권고(SMT 끄기·KSM 해제)는 소프트웨어 탈출과 페이지 중복 결합만 다루고 LLC 분할·vCPU 핀은 사용자에게 위임 — Rauch 실험은 코어 분리 상태에서도 DRAM 버스 등 패키지 단위 공유 자원이 남음을 보여줌 — 진짜 제거는 전용 호스트·정적 분할 하이퍼바이저(Jailhouse/Bao, 캐시 colouring)·seL4류뿐이며 모두 성능·비용 대가 수반, 전력·주파수 채널은 소프트웨어로 불가침
시사점
  • 'microVM = 완전 격리'라는 설계 전제의 교정 필요 — AI 에이전트 샌드박스는 격리(위변조 방지)와 컨파인먼트(신호 누출)를 별개 목표로 분리 정의해야 함
출처gctl.io 심층 분석 · AWS Nitro 화이트페이퍼 · cpu-chat 실험 결과 종합

채널은 하이퍼바이저 아래 실리콘에 존재한다. SMT/KSM/핀 설정만으로 안 뚫린다는 보장이 없고, 제거는 하드웨어 분배 정책(전용 코어·캐시 colouring·별도 호스트)의 비용 문제다. 따라서 실무 답은 완화+탐지의 조합이다.

Deep Dive 2

AI 에이전트 파밍 거버넌스
— 탐지·배치·투명성 논쟁

정책 분석
  • Rauch의 부수 폭로 — OpenAI·Anthropic 모델은 콥트 채널 구현 작업을 거부하고 오픈웨이트 모델이 완수: "실험실 태도가 개발자의 정확한 보안 시스템 구축을 방해할 수 있다" — 안전한 샌드박스 설계엔 이 분석이 필수라는 논거, 10월 Qwen '베이징 업로드' 원본 공개와 함께 오픈웨이트의 이중성(검증 가능성 vs 통제 불능) 논쟁 재점화
  • 멀티 에이전트 아키텍처의 새 설계 강령 — 기밀이 갈리는 에이전트는 최소 별도 프로세스, 적대적 환경에선 별도 하드웨어(V8 팀 "유효한 완화는 시크릿을 주소 공간 밖으로" / Chrome Site Isolation 교훈), 신뢰 경계가 곧 배치가 되는 'confidential placement' 요구, OpenAI도 인정한 '제거 아닌 탐지' 노선이 현실 표준
시사점
  • 에이전트 플랫폼 운영자는 하드웨어 카운터 기반 이상 신호(부하 패턴·캐시 이벤트·메모리 대역폭 통계) 모니터링 계층을 샌드박스 스택에 추가해야 함 — Vercel이 자칭하는 '실환경 탐지 우위' 논거(샘플링+통계)가 업계 벤치마크로 부상
출처@rauchg X 게시물 · gctl.io 방어 계층 분석 종합

이번 사안의 거버넌스 쟁점은 셋: (1) 연구·재현의 투명성과 실험실 거부 정책의 균형, (2) 에이전트 배치=신뢰 경계 원칙, (3) 제거 불가 전제 하 탐지 계층의 표준화. 모두 멀티 에이전트 서비스 도입 속도에 앞서 정리돼야 할 사안.

오늘의 조치 사항

즉시

즉시
자체 AI 에이전트 샌드박스 점검 — 기밀 수준이 다른 에이전트가 동일 호스트·동일 물리 코어(또는 SMT 형제)에서 도는지 배치 감사, 중요 워크로드부터 전용 코어 분리

금주

금주

V8/Site Isolation 교훈: 언어 샌드박스는 무결성 경계일 뿐 컨파인먼트 아님

Qwen·cpu-chat 사례가 보여준 오픈웨이트·재현 시대 — 공급자 검증 지점 확장
