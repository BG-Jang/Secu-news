2026년 9월 7일 보안 이슈 심층 분석. ICANN이 10월 12일 오전 1시(한국시간) 루트존 KSK(키 서명 키)를 교체 — DNSSEC 신뢰 유지 위한 주기적 업데이트로 2010년 도입 후 역대 두 번째. 미반영 캐시 DNS는 48시간 내 주소 조회 전면 실패, KISA 기준 전 세계 서버 95% 이미 반영 완료로 국지 장애 가능성 높음.

Overview · DNSSEC

루트 KSK
교체란
무엇인가

DNSSEC 신뢰 사슬의 최상단 갱신
기술 배경
  • DNSSEC은 도메인 정보(DNS 레코드)의 위·변조를 막는 암호 서명 체계 — 루트 존부터 최상위·권위 서버로 신뢰 사슬(Chain of Trust)이 이어짐
  • KSK(Key Signing Key)는 그 사슬 최상단인 루트 존의 서명을 담당하는 최상위 신뢰-anchor 키
  • 장기 노출 키는 유출·계산 능력 발전 위험 — 주기적 롤오버(교체)가 보안 유지 수단, 이번이 2010년 도입 후 역대 두 번째 교체
교체 시점과 원리
  • 2026.10.12(화) 오전 1시(KST) 전격 교체 — 이전부터 신규 키가 사전 게시되어 캐시 DNS가 미리 가져오도록 동작
  • 새 키를 반영하지 못한 캐시 DNS는 루트 서명 검증에 실패 → 해당 서버의 모든 도메인 주소 조회 불가(검증 실패=거부 원칙)
출처이데일리 - DNSSEC 보안 기술 설명 종합 · ICANN 롤오버 공지

이슈 해설: DNSSEC은 도메인 위·변조 방지 서명 체계, KSK는 루트 존 최상위 서명 키. 주기적 교체가 보안 유지 수단이며 10.12가 두 번째 롤오버. 미반영 캐시 DNS는 검증 실패 원칙에 따라 조회 전면 거부.

Guide 1 · 이용자·BIND/Unbound

이용자는 무조치
BIND·Unbound은
'작동 확인'까지

대상별 체크포인트 (1)
일반 인터넷 이용자
  • 별도로 암호키를 바꾸거나 설정을 변경할 필요 전혀 없음 — 통신사·기업 DNS가 정상이라면 평소대로 이용
BIND / Unbound 운영자 (필수 점검)
  • 두 소프트웨어 모두 최신 버전에서 루트 키 자동 갱신 지원 — 다만 "지원"과 "실제 작동"은 다름
  • BIND 확인: dig . DNSKEY +dnssec 응답에 새 KSK 존재 여부 대조, /var/named/의 key 파일 갱신 시점 확인, named 설정에서 trust-anchor 자동 업데이트 비활화 여부 점검
  • Unbound 확인: unbound-control list_anchor로 루트 키 상태 조회, auto-trust-anchor-file 존재·쓰기 권한 확인
  • 권장: 교체 전 최신 안정 버전으로 업데이트 후, 교체 당일 DNSSEC 검증 성공 로그 정상 여부 관찰
출처KBS · 연합뉴스 — 대상별 점검 권고 (버전·커맨드는 운영 관행 기반 편집 정리)

가이드 1: 일반 이용자 무조치. BIND·Unbound은 자동 갱신 지원 버전이어도 실제 작동을 확인해야 함 — dig DNSKEY, unbound-control list_anchor로 새 키 반영 상태 점검, 교체 당일 검증 로그 관찰 권장.

Guide 2 · PowerDNS·공통

PowerDNS는
'수동 확인'
반드시 필요

5.2.0 미만은 사전 업데이트 필수
PowerDNS 운영 기관 (최우선)
  • 암호키 자동 갱신 기능을 기본 지원하지 않음 — 방치 시 신규 키 미반영 피해군에 직접 해당
  • 신규 키가 기본 반영된 5.2.0 이상 버전 사용 여부를 반드시 수동 확인·업데이트
  • 확인: pdns_server --version로 버전 확인, 미만이면 교체일 전 업그레이드 완료 + 테스트 환경에서 DNSSEC 조회 검증
모든 DNS 운영자 공통 체크리스트
  • 내 캐시 DNS 인벤토리화: 업무망·생산망·클라우드·현장(OT)에 흩어진 재귀 조회 지점 전수 목록 — 숨은 라우터·구축형 앱서버 내장 resolver가 대표 사각지대
  • 교체 후 48시간 감시 강화: NXDOMAIN·SERVFAIL 급증, 검증 실패 로그 알림 설정
  • 비상 절차: 대체 DNS(2차 캐시·외부 resolver) 전환 순서 사전 훈련 — KISA 안내 채널 구독
출처KBS · 연합뉴스 — PowerDNS 5.2.0 이상 확인 당부 (커맨드는 운영 관행 기반 편집 정리)

가이드 2: PowerDNS는 자동 갱신 기본 미지원 — 5.2.0 이상 수동 확인·업데이트 최우선. 공통으로 캐시 DNS 인벤토리(숨은 resolver 포함), 교체 후 48시간 SERVFAIL 감시, 대체 DNS 전환 훈련.

FAQ

자주 묻는
질문

  • Q. 일반 사용자도 뭘 해야 하나요? — 아무것도 필요 없습니다. 통신사·회사 DNS가 정상이면 평소대로 이용하면 됩니다.
  • Q. 교체가 해킹 대응인가요? — 아닙니다. 2010년 도입 후 계획된 정기 롤오버(두 번째)로, DNSSEC 신뢰성 유지 목적의 정상 유지보수입니다.
  • Q. 권위(authoritative) 네임서버도 영향받나요? — 직접 영향은 캐시(재귀) DNS 중심입니다. 단 권위 서버도 DNSSEC 서명 체인을 사용한다면 루트 키 변경 안내를 확인하세요.
  • Q. 클라우드 DNS(AWS Route 53·Cloudflare 등)는? — 관리형 서비스는 사업자가 반영을 대행하는 것이 일반적이지만, 자체 구성한 재귀 resolver·컨테이너 내장 DNS는 대상이므로 인벤토리에 포함하세요.
  • Q. 장애가 생기면 어떻게 알 수 있나요? — 특정 내부망에서만 전 도메인 접속 실패 + SERVFAIL 급증이 전형적 신호입니다. 다른 DNS로 조회해 비교하면 즉시 판별 가능합니다.

Implications

보여주는
3가지

① 인터넷의 '예정된 장애'는 인벤토리 시험지
48시간 뒤면 아물 사안이지만, 내 캐시 DNS 몇 개인지 즉시 답 못하는 조직이 진짜 피해군 — 표준 이벤트에 대비하는 과정 자체가 자산 가시성 감사로 기능
② 자동화의 신뢰는 검증으로 완성된다
BIND·Unbound은 '자동 지원', PowerDNS는 '수동 확인' — 같은 인프라에 혼재한 갱신 모델 차이를 모르면 자동에 맡긴 줄 알고 놓친다. 자동화 여부까지 포함한 구성 문서화가 필요
③ DNSSEC 신뢰 사슬은 상시 유지 자산
도메인 하이재킹·DNS 스푸핑 방어선이 무너진 채 방치된 조직은 이번뿐 아니라 향후 모든 DNS 공격에 노출 — 롤오버를 계기로 DNSSEC 검증 활성화 상태 자체를 정기 점검 항목으로
